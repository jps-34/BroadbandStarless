# Maintenance: development, release and signing

Notes for the author. Nothing here is needed to use the script.

Python is used only by the maintenance tools of `tools/`, on the author's machine: it is never
packaged, installed or run by the script.

## 1. Initial publication

1. The update repository is already built in `docs/`. To rebuild it after changing the script:

   ```bash
   python3 tools/build_repo.py --user jps-34
   ```

2. Create the `BroadbandStarless` repository on GitHub (public, empty), then from the unpacked
   release folder:

   ```bash
   git init && git add . && git commit -m "BroadbandStarless 1.0.0"
   git branch -M main
   git remote add origin git@github.com:jps-34/BroadbandStarless.git
   git push -u origin main
   git switch -c dev && git push -u origin dev
   ```

3. On GitHub: *Settings > Pages > Build and deployment > Deploy from a branch*, branch `main`,
   folder `/docs`. The PixInsight repository is then served at
   `https://jps-34.github.io/BroadbandStarless/`.

4. Test: in PixInsight, *Resources > Updates > Manage Repositories*, add this URL, then
   *Check for Updates*. Until it is signed, the *Allow unsigned update repositories* security
   option is required.

## 2. Signing (later)

References: [Script code signing](https://pixinsight.com/doc/docs/ScriptCodeSigning/ScriptCodeSigning.html)
and [Update repositories](https://pixinsight.com/doc/docs/PIRepositoryReference/PIRepositoryReference.html).

Same keys as the other scripts (`.xssk` file, never in Git: the `.gitignore` excludes it). Order:
sign `scripts/BroadbandStarless.js` with **CodeSign**, run
`python3 tools/build_repo.py --user jps-34`, sign `docs/updates.xri` last, then commit.

## 3. dev branch, then production

`main` = production: GitHub Pages serves `docs/` from `main`, so everything that lands on `main`
reaches PixInsight. A new version goes to `dev` first.

**Only source to edit: `scripts/BroadbandStarless.js`** (V8, PixInsight 1.9.5 and later). `docs/`
(archive, digest, `updates.xri`) is generated by `tools/build_repo.py`.

Putting a new version on dev (example with the 1.0.1 archive):

```bash
cd <local repository folder>/BroadbandStarless
git switch dev
git rm -rq .
unzip -o <download folder>/BroadbandStarless-v1.0.1.zip -d <temporary folder>
cp -a <temporary folder>/BroadbandStarless/. .
git add -A
git status                     # check the list before committing
git commit -m "BroadbandStarless 1.0.1"
git push
```

Test in PixInsight: *Script > Execute Script File*, pick `scripts/BroadbandStarless.js` in the local
repository. The script runs without being installed; the production version stays in place.

Releasing once validated:

```bash
git switch main
git merge dev
git tag -a v1.0.1 -m "BroadbandStarless 1.0.1"
git push origin main --tags
git switch dev
```

Then, in PixInsight, *Resources > Updates > Check for Updates*.

## 4. Versions and history

* Numbering `MAJOR.MINOR.PATCH`: patch = bug fixed with no intended change in results, minor = new
  feature, major = incompatible settings or results.
* Each published version has its `vX.Y.Z` tag. The PixInsight repository (`docs/`) only serves the
  latest one; older versions stay available through git.
* Test builds are named `BroadbandStarless-<version>-dev.js`, with the same number in the window
  title; the repository keeps `BroadbandStarless.js`.
